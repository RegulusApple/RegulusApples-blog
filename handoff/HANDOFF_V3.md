## 1. V3 相对 V1/V2 补充的当前事实

### 1.1 Contents 已经不是“设计草案”，而是有明确行为契约的实现

V1/V2 记录过 Contents 的设计方向，但没有完整写清楚现在实际运行的状态机。当前实现位于：

- themes/halfold/layout/_partial/sidebar.ejs：文章页挂载 #article-toc；
- themes/halfold/source/js/main.js：解析标题、计算滚动状态、处理 hover/focus 和模块状态；
- themes/halfold/source/css/style.css：字号、虚化、颜色和过渡动画。

当前最终行为见第 2 节。尤其要记住：鼠标放到整个 Contents 模块上，含义是“当前结构上已经显示的条目取消虚化”，不是“把整棵目录树全部展开”。这条规则是根据用户对前一次误解的明确纠正确定的，后续不能重新按“模块 hover = 全层级展开”实现。

### 1.2 当前资源版本已经推进到 CSS 30、JS 21、Service Worker v14

当前模板与缓存资源的版本关系为：

~~~text

~~~

实际缓存名以源码中的 CACHE_NAME 为准。修改 CSS 或 JS 后，要同步检查 themes/halfold/layout/layout.ejs、source/sw.js 及校验脚本之间是否仍然一致。不要只改文件内容而忘记浏览器缓存版本，否则用户可能继续看到旧行为。

V2 已经记录了周刊页面和模板，但没有强调当前分流的关键实现：项目中的 scripts/regular-posts.js 会覆盖常规文章列表的生成逻辑，明确区分常规文章和带有 weekly: true 的正式周刊文章；项目仍依赖 hexo-pagination 提供分页能力。

因此：

- source/_drafts/ 中的周刊草稿不是正式线上内容；
- 正式周刊文章应放入 source/_posts/，并使用 weekly: true 与 layout: weekly-post；
- 正式周刊应进入 /weekly/ 和 Monthly Trace / 搜索所需的范围；
- 正式周刊不应意外出现在普通首页、普通归档、普通文章统计和普通文章列表中；
- 不要为了“简化生成器”删除 hexo-pagination 或 scripts/regular-posts.js，除非已经先确认所有入口的生成结果。

这是页面显示正确但生成边界可能错误时的优先排查点。

## 2. Contents 最终行为契约

本节是后续改动时的验收标准。若用户没有明确要求改变本契约，不能自行扩大或缩小它。

### 2.1 目录解析规则

- 仅在 page.layout === 'post' 的文章页渲染 Contents 模块。
- 解析文章正文中的 h2、h3、h4、h5、h6。
- 不显示标题前的自动编号。标题文字来自 heading 本身，编号若存在于文章文本中则属于文章内容，不由 Contents 再添加。
- 通过标题层级建立 parent / children 关系。
- 没有父级的条目通常是二级标题，也就是文章正文的 h2；这些条目是目录的根条目。
- 当前代码保留了多级标题通用能力，不要把实现硬编码成只能处理 h2/h3，除非用户明确要求改变标题层级范围。

### 2.2 默认和滚动状态

页面没有 hover 时：

1. 根级标题始终显示；
2. 根据滚动位置找出当前标题：优先使用已经越过文章顶部偏移量的最后一个标题，没有时使用当前可视标题；
3. 当前标题及其祖先构成 active path；
4. active path 中每个条目的直接子级可以逐层显示；
5. 与当前路径无关的更深层级继续隐藏；
6. 已经结构上显示、但不是当前标题的条目仍保留虚化；
7. 当前标题清晰显示并高亮。

这里的“显示”是结构上的可见，“清晰”是取消 blur 和提高 opacity，二者不能混用。

### 2.3 指向单个标题时的 hover / focus 状态

鼠标移到某个目录标题时：

- 被指向的标题高亮；
- 如果该标题有次级标题，只展示它下面的直接次一级标题；
- 目录以树结构继续计算，不能因为 hover 一个节点就无条件展示所有后代；
- 从父标题移动到它的子标题时，使用短暂延迟避免目录瞬间折叠；当前实现约为 180ms；
- 键盘 focus 与鼠标 hover 应保持同样的核心语义；
- 当前标题的滚动状态与 hover 状态叠加，hover 的目标优先作为当前交互焦点。

### 2.4 指向整个 Contents 模块时的状态

鼠标进入整个 Contents 卡片 / 模块时：

- 不改变当前目录树的层级展开范围；
- 只对“当前结构上已经显示”的条目取消虚化、提高不透明度；
- 隐藏的更深层级仍然隐藏，不因为模块 hover 自动出现；
- 如果同时指向某个具体标题，具体标题仍使用单条目 hover 的橙色高亮和次级标题展开规则；
- 鼠标离开模块后，恢复滚动状态下的虚化和展开状态；
- 整个过程应使用自然过渡，不产生突然跳变。

当前实现使用的关键状态和 class 包括：

~~~text
moduleHovered
hoveredEntry
parentStack
.toc-subitem
.is-revealed
.is-current
.is-hovered
.is-module-clear
~~~

改动时应优先在这套契约上修正，而不是另起一套互相冲突的目录状态。

### 2.5 当前视觉参数

当前目录文字约为：根条目 14px、子条目 13px；默认 blur 约为 3px。层级展开使用 max-height、margin-top、opacity、transform 以及 filter 的过渡动画。

如果用户再次说“字体太小”或“动画不自然”，必须先确认是：

- 所有 Contents 字体都要变大，还是只改子级；
- 只改视觉字号，还是连卡片宽度 / 文章可用宽度一起调整；
- 只改模糊清晰过渡，还是改变层级出现与消失的时序；
- 桌面端和移动端是否采用同一组参数。

不能仅根据一句“再大一点”自行改动多个维度。

## 3. 必须使用 grilling 的需求规则

这是用户明确要求写入 V3 的工作纪律：后续凡是涉及视觉交互、Contents、模块、动画、虚化、显示层级或发布边界的需求，都要多用 grilling 回滚和澄清需求。需求没有明确之前，不应直接进入代码修改。

### 3.1 为什么必须先 grilling

本项目已经发生过一次典型的语义误解：用户说“鼠标放到模块上时，模块要整个显示出来”，实现被误读成“整个目录层级展开”；用户随后明确纠正，真正含义是“当前显示的目录条目取消虚化，但不展开整棵目录树”。

因此，以下词语不能直接当成实现指令：

~~~text
显示出来 ≠ 展开层级
展开 ≠ 取消虚化
清晰 ≠ 可见
模块 hover ≠ 单条目 hover
高亮 ≠ 改变目录结构
恢复 ≠ 回滚到上一个代码版本
~~~

### 3.2 触发流程

接到相关需求后，先完成以下流程：

1. 先读取项目要求的 C:/Users/Regulus/.agents/skills/SKILLS_INDEX.md；
2. 命中后完整读取 C:/Users/Regulus/.agents/skills/grilling/SKILL.md；
3. 先检查当前代码、页面范围、已有状态和最近变更，事实由 agent 自行查明；
4. 对仍然属于产品决策的问题，用 grilling 一次性提出当前全部决策前沿；
5. 每个问题编号，给出推荐选项和影响，避免只问一个局部问题导致反复返工；
6. 用自己的话复述完整状态机，特别是默认、滚动、单标题 hover、整个模块 hover、离开后的恢复、键盘 focus 和移动端行为；
7. 等用户确认后再修改代码。

不要把能从仓库、生成结果或浏览器状态查到的事实问题丢给用户。grilling 用来确认“应该怎样”，不是让用户替 agent 做排查。

### 3.3 每次 Contents 需求至少要问清楚的维度

除非用户已经明确给出答案，否则至少确认：

- 作用页面：只改文章页，还是首页 / 归档 / 周刊页也改；
- 标题范围：只处理 h2/h3，还是保留 h2–h6；
- 编号来源：去掉目录自动编号，还是连文章标题文字里的编号也去掉；
- “显示”的定义：改变结构可见性，还是只取消虚化；
- “展开”的定义：展示直接子级，还是展示所有后代；
- “清晰”的定义：取消 blur、提高 opacity、改变颜色，还是三者全部改变；
- 交互优先级：滚动当前、标题 hover、模块 hover、键盘 focus 冲突时谁优先；
- 离开行为：立即恢复、延迟恢复，还是保持最后状态；
- 动画边界：只动画层级出现，还是 blur / opacity 也动画；
- 响应式行为：移动端是否保留 hover 语义，触摸端用什么替代；
- 可访问性：键盘 focus、减少动态效果设置、对比度和触控目标是否需要保持；
- 发布边界：只做本地预览、上传 Sites，还是上传后再验证线上状态。

### 3.4 确认语言要有上下文

只有在复述完整规则后，用户的“对”“好”“就是这个”才可以视为确认。若用户只回复一个模糊的“可以”，但前面同时存在多个未决维度，应继续 grilling，不要选择性地把它当成全部批准。

如果用户说“不是这个”“回滚一下”“我指的是……”：

- 先停止继续扩展当前实现；
- 复述当前实现和用户想要的目标差异；
- 询问是撤销本次行为、保留行为但改参数，还是回到某个明确历史状态；
- 明确作用范围和是否需要重新上传；
- 用户确认后再采取回滚或修正动作。

## 4. 回滚与需求变更规则

### 4.1 先区分四类问题

收到“回滚”或“改回去”时，先判断问题属于哪一类：

| 类别 | 典型表现 | 首要处理 |
| --- | --- | --- |
| 需求误解 | 实现语义与用户想法不一致 | 用 grilling 重述和确认，不盲目恢复代码 |
| 源码行为错误 | 状态机、选择器或动画本身有 bug | 定位具体文件和状态，做最小修复 |
| 生成 / 缓存问题 | 源码正确但页面仍显示旧版本 | 重建、检查资源版本和 Service Worker |
| 发布版本问题 | 本地正确，线上仍是旧版或错误版 | 核对实际 Sites 版本和部署状态 |

“回滚”不天然等于 git reset，更不等于删除当前工作。

### 4.2 本地源码回滚安全规则

- 先运行 git status --short、git diff 和目标文件级 diff；
- 先确认要撤销的确实是哪个文件、哪个行为、哪个提交或哪个未提交片段；
- 未经明确授权，不使用 git reset --hard、git checkout --、git clean -fd；
- 不使用会覆盖用户未提交工作的批量恢复命令；
- 如果只是最近一个局部改动，优先用针对性补丁修正；
- 如确实需要撤销已发布的源码变更，优先创建清晰的独立 revert 提交，保留历史，再重新构建和验证；
- 回滚本地源码和回滚线上 Sites 部署是两件事，不能用一个动作假装完成另一件事。

### 4.3 发布回滚规则

需要线上回滚时：

1. 先确认用户要回滚的是“行为”“文章内容”还是“整个站点版本”；
2. 查明可用的 Sites 已保存版本和当前线上版本；
3. 如果目标版本不唯一，先向用户说明候选版本，不凭时间猜测；
4. 只在用户明确要求发布 / 回滚线上版本后执行 Sites hosting 流程；
5. 发布后重新检查站点状态、隐私策略和目标页面；
6. 不在交接文档、日志或回复中暴露短期凭据、内部项目 ID 或令牌。

### 4.4 需求变更记录格式

后续若 Contents 或其他核心交互再次变化，交接中至少记录：

~~~text
原行为：
用户实际想要：
经过 grilling 确认的规则：
修改范围：
是否影响移动端：
是否影响缓存版本：
是否已本地验证：
是否已上传 / 发布：
~~~

这样下一位 agent 可以区分“代码曾经这样做过”和“用户最终确认要这样做”。

这些功能可以在未来单独 grilling，但不能因为“看起来还没完成”就顺手接入。用户已经明确表示，评论、音乐、留言板是否真正接入要单独决定。

## 8. 其他已知陷阱

### 8.1 本地分支不等于线上最新版本

本地 origin/main 可能只是历史仓库远端，不应据此推断线上 Sites 当前版本。判断线上版本时，以 Sites 实际绑定和部署状态为准；判断本地变更时，以当前工作树、提交历史和构建结果为准。

### 8.2 资源版本、Service Worker 和生成目录必须一起看

样式或脚本修改后，如果只看源码而不重建，或者只重建而不更新 Service Worker 缓存版本，可能得到“代码已经改了但页面不变”的假象。验证时应同时检查：

- layout 中引用的 query version；
- source/sw.js 的 cache name 和 APP_SHELL；
- 生成后的 HTML、CSS、JS 和内部引用；
- 浏览器是否仍在使用旧 Service Worker。

### 8.3 页面源文件和模板配置可能是两层来源

相册、音乐、留言板等页面可能只在 Markdown front matter 中提供页面壳，再由模板读取主题配置或数据。遇到“页面有了但内容为空”时，应先追踪数据来源链，不要只修改 Markdown 页面文本。

### 8.4 文章标题变化会影响目录和锚点

修改文章 heading 可能同时影响：Contents 文本、slug / anchor、搜索引用和历史链接。修正标题时，应检查生成站点中的锚点与内部引用，不要只看正文视觉结果。

### 8.5 私有站点的验证口径

线上站点为私有访问时，外部未授权环境可能无法验证页面。此时要明确区分“部署完成”“所有者可访问”和“匿名访问通过”，不能把其中一个结论写成另一个结论。

## 9. 建议技能

接手或继续改动时，按任务选择以下技能：

- handoff：更新交接文档，先读项目要求的 skills index，再读完整技能说明；

- sites:sites-hosting：用户明确要求上传、发布、查看部署或管理站点时使用；
- browser:control-in-app-browser：用户明确要求浏览器交互、截图、DOM 或线上页面验证时使用；
- diagnosing-bugs：用户明确报告页面错误、构建失败、部署失败、性能问题时使用；
- research：需要查阅外部官方文档、规范或技术事实时使用；
- writing-for-agents：只有在修改 AGENTS.md、技能或 agent 规则时使用。
